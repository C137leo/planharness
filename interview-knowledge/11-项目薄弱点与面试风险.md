# 11 项目薄弱点与面试风险

## 这些说法不要再用

| 容易说错 | 当前准确说法 |
|---|---|
| 规则先兜底，LLM再分类 | 生产聊天唯一走semantic_runtime的结构化模型语义规划 |
| 整个项目由LangGraph调度 | Graph用于独立补丁审批；统一聊天自定义编排 |
| 有通用独立Verifier和自动回滚 | 各边界有具体校验；全局goal_verified仍为null，事务证据未统一 |
| 几个工具都success就是用户目标完成 | 目标提取、实际效果和未满足要求须另看；回复不是证据 |
| Profile改了就计划重算 | 原本地profile.update不自动重算训练/营养 |
| 有MealLog就能聊天记所有饮食 | API/页面存在与聊天能力覆盖分开核对 |
| 待支付15分钟后所有unknown都可忽略 | 只有已核实未支付适用期限；未知副作用仍需对账 |
| 订单请求幂等等于远端exactly-once | 本地声明防重复派发，无法保证远端原子一致 |
| Console实时显示全部工具事务 | 当前批次事件+已持久化记录；无SSE/全工具事务链 |
| 审计链无法篡改 | 可发现一致性破坏，未外部锚定，整库写权仍有风险 |
| 支持向量RAG与语义embedding | 对比实现是hash-ngram，不是语义embedding服务 |
| 模型挂了业务全部正常 | 聊天语义规划不可用，其他接口按各自降级 |
| 有Docker/systemd就是已生产验证 | 部署模板和生产实测分开，规模数据尚缺 |
| 当前项目准确率是旧报告百分比 | 旧成绩绑定旧版本与数据，不能外推当前版本 |

## 实际技术债与改进顺序

1. **正确性证据**：补齐整体目标达成、各工具提交/回滚、商务对账关联；先覆盖复杂多轮和部分成功，避免先做漂亮时间线。
2. **发布与恢复**：验证PG迁移、并发、中断窗口、保留周期；把启动期加法补齐逐步纳入可审阅迁移管理。
3. **体验与观测**：实时执行反馈、长历史性能、更细调用耗时、令牌/成本数据。先明确数据采集来源再加展示。
4. **能力一致性**：独立旧API、生成器与当前聊天覆盖边界继续收敛；业务退役需兼容窗口，不能为简历精简而删代码。

这些是改进建议，不是已完成成果；不会因为写进本指南就自动变成当前迭代承诺。

## 产品侧诚实边界

2026-11-10的体验评审是真实问题来源，能说明为什么要调整语言理解、授权和数据一致性；它不能证明当前版本依然同样差，也不能证明改完代码后用户满意度提升。原14轮场景、真机、无障碍、模型实测应各自重新验收。

不把健身建议讲成医疗诊断，不把宏量营养/时长估算讲成实测生理结果，不承诺官方门店和库存永远可用。
