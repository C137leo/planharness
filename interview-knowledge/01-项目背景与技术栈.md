# 01 项目背景与技术栈

## 为什么做

用户的时间、器械、饮食偏好和训练完成情况会变化。仅生成一份计划无法解决持续调整问题：同一句“先保留这三个动作，练到50分钟，晚上吃牛肉”同时包含选择、数值目标和餐次范围；一处误读可能让整份安排漂移。

因此项目关注“理解之后能否可靠落到业务对象”，而不只关注回答是否自然。当前仍是工程验证型应用，不能在没有用户研究和线上指标时描述成成熟消费级产品。

## 实际技术选择

| 技术 | 当前用途 | 选型取舍 |
|---|---|---|
| Vue3 + TypeScript + uni-app | 共享页面、对话、结构化确认、H5/小程序构建 | 共用UI和业务客户端；构建通过不等于真机通过 |
| Python3.12+ + FastAPI | 认证API、依赖注入、请求模型 | 便于表达结构化协议和接口测试 |
| SQLAlchemy | 业务模型、事务、唯一约束、版本与日志 | 直接Session服务层，没有抽象成复杂DDD基础设施 |
| SQLite / PostgreSQL | 本地开发隔离测试 / 部署模板 | SQLite锁配置不能证明PG并发正确 |
| DeepSeek-compatible客户端 | 结构化语义规划、确认控制与受限修复 | 不是微调模型；无密钥时生产聊天不能靠旧规则替代 |
| LangGraph + checkpointer | 独立补丁审批图的挂起/恢复 | 不承担统一聊天所有编排 |
| Node skill桥接 | 独立计划生成与确定性引擎 | 额外子进程/部署依赖，缺失按原服务处理 |
| MCP客户端 | 工具发现、Schema校验、门店与订单服务 | 能力受官方供应、凭证和下单开关制约 |
| 本地BM25 / hash-ngram / RRF | 自建知识与外部语料对比接口 | hash向量不是外部语义embedding |

证据：[依赖声明](../backend/pyproject.toml)、[前端依赖](../frontend/package.json)、[应用装配](../backend/app/main.py)、[skill桥接](../backend/app/skill/bridge.py)。

## 为什么暂不做微服务

核心难点是语义、范围、授权与副作用，不是服务拆分。模块化单体便于明确数据库事务和本地测试。没有证据支持用MQ/Kubernetes/Redis来包装当前实现。规模增长后先测量锁等待、模型耗时和历史查询，再决定是否拆执行任务或观测存储。
