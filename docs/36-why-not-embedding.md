# 30 条知识库在哪、够不够、面试怎么答"为什么不用 embedding"

## 1. 30 条放在哪里

**源头文件**：`backend/app/knowledge/seeds.py` 里的 `SEEDS`（30 个 dict）。
另有 13 条**可选扩展**（清单型）由 `data/knowledge/expanded.json` 提供，
启动时一起入库——当前库里是 **43 条**（30 人工 + 13 生成）。

```python
{"id": "knee-pain-swap", "title": "膝痛时的动作替代", "body_part": "knee",
 "topic": "safety",
 "content": "深蹲或弓步时膝盖疼，先暂停高屈膝动作…",
 "tags": ["膝", "膝盖", "替代", "疼痛"],
 "source_title": "Mayo Clinic：运动损伤",
 "source_url": "https://www.mayoclinic.org/..."}
```

**落库**：应用启动时 `app/main.py` 调 `seed_knowledge(session)`，
按 `id` 幂等 upsert 到 `knowledge_chunks` 表（`models.KnowledgeChunk`）：

| 字段 | 说明 |
|---|---|
| id / title / body_part / topic / content / tags | 检索与展示 |
| source_title / source_url | **没有出处不允许进库**（有测试校验） |
| version | 条目版本（预留） |
| embedding | **预留字段，目前为空**（上向量时直接填） |

检索时读的是**数据库**（`retriever.search(db, ...)`），不是文件；
改 `seeds.py` 后重启即生效，id 不变则原地更新。
扩展文件删掉、重启，库里就回到 30 条（`seed_knowledge` 不再 upsert `kb-*`，
但旧行仍在库里；要彻底回滚需手动删 `kb-%` 行或重建库）。

自查：

```bash
cd backend
.venv/bin/python -c "
from app.knowledge.seeds import SEEDS
from collections import Counter
print(len(SEEDS), Counter(s['body_part'] for s in SEEDS), Counter(s['topic'] for s in SEEDS))
"
```

## 2. 30 条够不够？——够 demo，不够产品

当前分布：

```
按部位：general 18、back 3、knee 2、legs 1、chest 1、core 1、shoulder 1
        手腕 1、手肘 1、脚踝 1
按主题：nutrition 9、safety 9、technique 7、recovery 5
```

**为什么 demo 能跑**：30 条是"结论型"知识（该怎么做、要不要就医），
加上 600 条"事实型"外部语料（动作/食物），再加 skill 的动作编排；
一次回答只需要 1–2 条引用，命中就能答。

**什么时候会露馅**：

1. 用户追问细节（"膝痛具体做哪几个替代动作、几组"）→ 只有一条 100 字内容，深度不够；
2. 脚踝/手腕/手肘各只有 1 条"替代"条目，没有独立的红旗/分级，深问会不够用；
3. 特殊人群（孕期、高血压、糖尿病、腰痛伴腿麻）→ 完全没有；
4. 一条内容混多个结论（蛋白质那条我们刚拆成两条）→ 引用容易错配；
5. 没有 `verified_at` / 指南版本 → 无法回答"这条是什么时候核对的"。

**建议的扩容路线**（不是拍脑袋堆量）：

| 阶段 | 条数 | 做什么 |
|---|---|---|
| 现在 | 30 | demo：减脂 + 3 个动作 + 三餐；腕/肘/踝已有替代条目 |
| 一次拆分 | **80–120** | 一条只讲一个结论；腕/肘/踝补红旗和分级，再补孕期/高血压/糖尿病禁忌、补剂、睡眠、平台期、外食 |
| 产品级 | **150–300** | 每个部位 8–15 条（要领/常见错误/替代/红旗）、营养 40–60 条、恢复 20–30 条 |
| 再往上 | >500 | 需要按人群/目标分库，配合检索过滤，否则互相稀释 |

我的判断：**30 条是"演示规模"，不是"生产规模"**；
但也不必一上来堆 500 条——先按"一条一结论"拆到 100 条左右，收益最大。

## 2.1 用 600 条语料扩充：能扩什么、不能扩什么

可以，但**只能扩"事实型"，不能扩"结论型"**。

| 能生成（数据可推导） | 不能生成（必须人写 + 机构出处） |
|---|---|
| "练胸的常见动作清单"（8 个动作 + 器械/难度） | "膝痛应该换什么动作" |
| "蛋白质来源清单（每 100g 热量/蛋白）" | "什么情况必须就医" |
| "主食/蔬菜/水果/坚果清单" | "孕期/高血压/糖尿病能不能练" |
| 出处：free-exercise-db（Unlicense）/ USDA（CC0） | 出处：指南/机构，且要逐条核对 |

实现：

```bash
cd backend
.venv/bin/python scripts/expand_curated_from_rag.py
# 生成 data/knowledge/expanded.json（13 条：7 个部位动作清单 + 6 个食物品类清单）
# 重启服务后 seed_knowledge 会一起 upsert（id 前缀 kb-）
```

效果（`/knowledge/search?q=练胸有哪些动作`）：

```
kb-ex-chest  练胸的常见动作清单   score 32.0
  练胸的常见动作（按器械/难度）：俯卧撑（自重/入门）、哑铃卧推（哑铃/入门）、
  哑铃飞鸟、杠铃卧推、绳索夹胸、上斜哑铃卧推、上斜杠铃卧推、颈推。
```

**为什么值得做**：单条动作语料只能回答"这个动作怎么做"，
而"练胸有哪些动作""高蛋白吃什么"是**列表型问题**，
一条聚合条目比 8 条分散条目更容易被检索到、也更适合塞进模型上下文。

**边界**：这些条目带 `generated: true`、`tags` 里有"自动生成"，
评测/测试里也会校验出处；它们回答不了"该不该做/要不要就医"，
那类问题仍然只有 30 条人工结论（加指南引用）能做。

## 3. 面试怎么答"为什么不用 embedding"

### 30 秒版

> 不是不会用，是**现在不需要，而且我们有评测数据支撑这个决定**。
> RAG 的核心是"检索 + 引用校验"，检索器用 BM25 也是 RAG。
> 线上两套检索现在都是 BM25：43 条知识库在 84 条评测上 hit@3 100%、hit@1 92%；
> 600 条动作/食物在 60 条评测上 hit@3 95–100%，加哈希向量没有提升。
> 600 条那套的口语查询 hit@3 是 87%、hit@1 是 60%；hit@1 低有一部分是评测口径，
> 真正的失败是"新手先练什么"这类计划型问题——语料里没有对应条目。
> 所以我把"什么时候该换"写成了触发条件：
> 口语查询占比上来、或 hit@3 掉到 85% 以下，就换成 **BM25 + 真 embedding 混合**，
> 只替换 `_embed()`，`KnowledgeChunk.embedding` 字段已经预留好了。

### 展开版（四个理由）

1. **规模**：<1000 条语料，词面重合高，向量收益抵不过复杂度；
2. **查询形态**：术语/事实型（动作名、食物名），BM25 的精确匹配反而更强；
   向量对"精确 ID/术语"没有优势；
3. **可解释与可审计**：每条命中能说出"因为标题/tags/正文命中"，
   出了问题能改规则；embedding 漂移、模型换版本要重建索引，排查成本高；
4. **成本与依赖**：BM25 是内存计算（600 条建索引 12ms），
   不需要 embedding 服务、不需要 GPU、不增加网络故障点。

### 如果面试官继续追问

**Q：向量不是更先进吗？**
A：向量解决的是"换个说法也能搜到"，不是所有检索问题的通解。
我们用 60 条 id 级评测量过：字面查询 BM25 100% hit@3，口语查询 60% hit@1——
**该换的信号很清楚，但换的是"混合"，不是"把 BM25 扔掉"**。

**Q：那你什么时候会换？**
A：三个触发条件任一满足：
① 真实查询里口语/同义占比超过 30%；
② hit@3 掉到 85% 以下；
③ 语料超过 2–5k 或跨语言。
换的时候：接 OpenAI 兼容 embedding（bge-m3 / text-embedding-3-small），
600 条成本几分钱；存 `KnowledgeChunk.embedding` 或 pgvector；
**BM25 与向量 RRF 融合**，不是二选一；上线前后跑同一套评测。

**Q：embedding 能解决口语查询吗？**
A：能解决"同义/转述"（前侧→股四头肌），**不能解决**用户画像（"新手"）、
否定（"不是练腿是练臀"）、品类层级（油 vs 坚果）——这些要靠 query 理解或元数据过滤。
所以我们没有把它当银弹。

**Q：怎么证明你的评测不是自欺欺人？**
A：评测集是 60 条人工指定目标 id（不是"标题含关键词"），分 literal/paraphrase/food 三类；
失败案例逐条列出来（减脂期/新手/橄榄油），并且承认评测是我一个人标的、
没有第二标注者——这是它的局限。

## 4. 一句话总结

**30 条够 demo 不够产品；关键词够术语不够口语；不用 embedding 是"评测后的选择"，
不是"没做过的空白"——而且换的成本已经被设计成一个函数（`_embed()`）。**
