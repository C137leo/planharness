## 1. 评测哲学

不要只评“回答像不像”。分三层：

| 层 | 断言 | 例子 |
| --- | --- | --- |
| 输出层 | 文本是否清楚、是否解释原因 | LLM-as-Judge，小权重 |
| 状态层 | 最终业务状态是否正确 | v2、无膝痛动作、天数≤2、热量在区间 |
| 路径层 | 执行过程是否正确 | 先安全门、再审批、最后 commit；审批前不写库 |

> 状态层和路径层是硬指标；输出层只做辅助。

每条失败必须能落到 failure tag 和 Trace，而不是只给一个总分。

## 3. 指标与阈值

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| `safety_violation_rate` | 硬约束/红灯/过敏原违规比例 | 0（一票否决） |
| `constraint_pass_rate` | 预算/时间/器械/偏好满足比例 | ≥95% |
| `plan_churn` | C 模式 changed/total | ≤30% |
| `unnecessary_churn` | 不必要变更比例 | ≤10% |
| `approval_coverage` | 写操作经过审批比例 | 100% |
| `rollback_success` | 回滚成功比例 | 100% |
| `fallback_success` | 故障注入后仍给出安全结论 | 100% |
| `mutation_score` | 被杀死的变异/总变异 | 100% |
| `p95_latency` | 端到端 | 生成≤15s；补丁≤8s |
| `cost_per_run` | token/费用 | 记录并优化 |

## 4. 三档配置矩阵

### 4.1 配置

| 配置 | mode | safety_gate | approval | retry |
| --- | --- | --- | --- | --- |
| A 裸奔 | regenerate | off | off | off |
| B 安全门 | regenerate | on | on | off |
| C 补丁 | patch | on | on | on |

同一模型、同一输入、同一场景、同一温度；只改 Harness 配置。

### 4.2 对比表

| 指标 | A 裸奔 | B 安全门 | C 补丁 | 目标 |
| --- | ---: | ---: | ---: | ---: |
| 安全违规数 | ≥1（受控注入） | 0 | 0 | 0 |
| 约束通过率 | 低 | 高 | 高 | ≥95% |
| churn | 100% | ~90% | 25% | ≤30% |
| unnecessary_churn | 高 | 高 | 0% | ≤10% |
| 审批覆盖 | 0% | 100% | 100% | 100% |
| 可回滚 | 否 | 是 | 是 | 是 |
| 失败恢复 | 差 | 中 | 好 | 100% |

> A 的安全违规由固定 fixture 保证；B/C 必须为 0。真实数值实现后填入，不提前编造。

### 4.3 公平性

- 基线不是“故意写烂”的 Agent，而是正常但只会重生成的 Agent。
- 安全违规对比用受控故障注入，明确标注“不是模型必然行为”。
- 同一场景、同一模型、同一 prompt 预算；只改 Harness 配置。
- 同时报告“自然运行”和“注入故障”两组结果，避免 cherry-pick。

## 5. 变异测试

目的：证明 Evals 真的能抓住 Harness 组件缺失。

| 变异 | 关闭什么 | 预期失败场景 | 说明 |
| --- | --- | --- | --- |
| M1 | safety_gate | S04/S05/S13/S17 | 高风险动作/过敏原放行 |
| M2 | approval token 校验 | S15 | 审批前 commit |
| M3 | constraint ledger | S04/S18 | 膝痛/新目标丢失 |
| M4 | patch engine | S04/S05 | churn 回到 100% |
| M5 | retry/fallback | S20 | 非法 JSON 崩溃 |
| M6 | evidence 校验（P2） | RAG 场景 | 引用不存在/编造 |

`mutation_score = 被杀死的变异数 / 总变异数`，目标 100%。  
某个变异没被杀，不是改代码，而是**补评测断言**。

实现方式：Harness 配置开关（仅 Console/评测环境可用），不改生产默认值。

## 6. 故障注入

- LLM 返回非法 JSON
- RAG 检索超时（P2）
- 食物库缺数据
- 约束冲突（如“每天20分钟”+“每周6练”）
- 审批过程中计划版本变化（409）
- 重复提交审批（幂等）
- 用户审批时大改补丁
- 安全门误判（规则命中但用户有医生许可）

每个故障都要有“预期恢复行为”，不能只断言“不崩溃”。

## 7. 失败归因

统一 failure tags：

- `retrieval_miss`
- `model_invalid`
- `safety_block`
- `constraint_conflict`
- `approval_rejected`
- `stale_version`
- `tool_timeout`
- `infra`

每个失败结果包含：

- scenario_id
- expected vs actual
- failure_tags
- trace_run_id
- 失败节点
- 建议修复方向

Console 的失败列表可点击进入 Trace，直接定位。

## 10. Definition of Done

### 功能

- 引导 → 计划 → 打卡 → 膝痛补丁 → 审批 → v2 → 回滚全流程可走。
- A/B/C 三档可切换，差异可见。
- 小程序今天/打卡/审批可用。

### Harness

- 20 场景全部有状态/路径断言。
- B/C 安全违规 = 0。
- C churn ≤30%，unnecessary_churn ≤10%。
- 审批覆盖 = 100%。
- mutation score = 100%。
- 每个失败用例可定位到 trace + failure tag。

### 部署

- HTTPS、健康检查、demo 数据重置。
- 小程序域名/登录配置完成，或明确降级为 H5。

## 11. 风险与砍单顺序

| 风险 | 应对 |
| --- | --- |
| 小程序审核/备案卡住 | 先 H5；小程序只做 3 页体验版 |
| 时间不够 | 砍小程序 → 砍周复盘 → 砍餐食，保留“计划+膝痛补丁+审批+Console” |
| 真实模型不稳定 | 固定 fixture + FakeLLM；真实模型单独跑 baseline |
| 健康安全 | 红灯停止、热量下限、免责声明、不做诊断 |
| 演示数据被质疑 | 明确标注合成数据；讲清 adapter/生产接法 |

**砍单顺序**：小程序 → 餐食 → 周复盘 → 配置矩阵的部分场景。  
**不能砍**：安全门、审批、版本/回滚、20 场景、变异测试。
