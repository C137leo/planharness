# 知识库扩容：有哪些现成数据源、多少条才值得上 RAG

## 1. 现成数据源（按许可从宽松到严格）

| 数据源 | 内容 | 规模 | 许可 | 适合用在哪 |
|---|---|---|---|---|
| [free-exercise-db](https://github.com/yuhonas/free-exercise-db) | 动作库（名称、肌群、器械、图片、步骤） | **800+ 动作** | **The Unlicense（公共领域）** | 动作要领/替代动作候选/动作图 |
| [USDA FoodData Central](https://fdc.nal.usda.gov/api-guide.html) | 食物营养成分（能量、蛋白、脂肪、微量） | 数十万条 | **公共领域（CC0 1.0）**，需免费 API key | 食材营养、配餐校验 |
| [Open Food Facts](https://world.openfoodfacts.org/data) | 包装食品条码与营养 | 300 万+ 商品 | **ODbL**（衍生数据库要同样开放） | 扫码/包装食品识别 |
| [wger](https://wger.de/api/v2/) | 社区食材库 + 训练计划 | API 实测 **306 万+ 食材** | 代码 AGPL-3.0；**数据许可以站点声明为准** | 英文食材名/营养（需先核对许可） |
| 中国食物成分表（CFCT） | 中国食物营养 | 数千条 | **版权图书**，需授权 | 中国食材最准确，但要买授权 |
| ACSM / NHS / WHO / Mayo / 中国居民膳食指南 | 训练与营养指南 | — | 文本版权，**摘要+链接引用可行**，整段搬运不行 | 结论性知识条目（我们现在的做法） |
| ExRx / 薄荷 / 丁香医生 | 动作库、食物库 | — | 商业/版权，**不要抓** | 只可参考，不可入库 |

### 建议的组合

- **动作库**：用 free-exercise-db（Unlicense）替我们手写的 302 动作快照做补充，
  图片/步骤都能直接用；
- **中国食材营养**：优先买 CFCT 授权，或用 USDA + 人工映射常见中餐食材；
- **包装食品**：Open Food Facts（注意 ODbL 的传染性）；
- **结论性知识**（"膝痛该换什么动作""蛋白质吃多少"）：继续自己写 + 机构出处，
  这类内容的价值在"经过筛选与压缩"，不在数量。

## 2. 多少条才值得上 RAG？——看查询形态，不是看条数

没有魔法数字，但可以给一个工程决策表：

| 语料规模 | 检索方案 | 判断依据 |
|---|---|---|
| < 50–100 条 | 关键词 / bigram / BM25 + 元数据过滤 | 词面重合度高，向量收益抵不过复杂度（**我们现在 30 条就属于这一档**） |
| 100–500 条 | BM25 + 向量混合（hybrid），带 rerank | 用户开始换说法、同义词多，纯关键词 hit@3 掉到 80% 以下 |
| 500–5k 条 | 向量为主 + 元数据过滤 + rerank | 人工维护关键词表不现实 |
| > 5k 条 | 必须向量索引 + 分块策略 + 去重 + 评测集 | 语料内部重复/冲突开始显著 |

换算到我们的场景：

- 只扩到 **200–300 条**精选知识（动作要领 × 部位、安全、恢复、营养、常见问题）：
  关键词 + 同义词表仍然够用，**不必上向量**；
- 引入 free-exercise-db 的 800 动作（每个动作拆"要领 / 常见错误 / 替代"3 条）→
  **约 2500–4000 chunks**，这时候 RAG（向量 + rerank）才真正划算；
- 再加 USDA/CFCT 的食材营养（几千条）→ 直接进入"必须向量"的区间。

**结论**：不是"到 500 条就该上 RAG"，而是"当关键词检索的 hit@3 撑不住真实问法时"才上。
先建 40–60 条评测 query，量一下再决定。

## 3. 判断要不要换检索：三个指标

1. **hit@3 ≥ 85%**：真实问法（含口语、同义）里，正确条目出现在前 3 的比例；
2. **引用覆盖率 100%**：每条回答都能指到具体来源（我们已强制）；
3. **无答案率可解释**：拒绝回答的比例应该在预期内，而不是因为检索漏了。

先跑评测再换方案，否则很容易"上了向量、效果没变、复杂度翻倍"。

## 4. 扩容时的入库规范（比现在多三个字段）

```json
{
  "id": "knee-swap-01",
  "title": "膝痛时的动作替代",
  "content": "……（一条只讲一个结论，60–160 字）",
  "body_part": "knee",
  "topic": "safety",
  "tags": ["膝", "替代", "疼痛"],
  "source_title": "Mayo Clinic：运动损伤",
  "source_url": "https://www.mayoclinic.org/...",
  "license": "citation-only",
  "guideline_version": "2024-03",
  "verified_at": "2026-11-07",
  "evidence_level": "guideline"
}
```

分块原则：

- **一条一个结论**，标题写清适用人群（"一般成年人" vs "力量训练者"）；
- 保留出处与版本，方便指南更新时定位要改哪条；
- 中英文双语条目分开存，别混在一个 chunk 里（检索会互相稀释）。

## 5. 落地顺序建议

1. 用 free-exercise-db 补动作库（许可最干净，收益最直接）；
2. 把现有 30 条拆到 80–120 条（一条一结论），先不换检索；
3. 建 40–60 条评测 query，量 hit@3；低于 85% 再考虑 hybrid；
4. 引入 pgvector（Postgres 已在用）+ 一个 embedding 模型，成本约几分钱；
5. 包装食品/中国食材有授权之后再做，避免许可风险。

## 6. 许可提醒

- **ODbL（Open Food Facts）有传染性**：基于它生成的衍生数据库也要 ODbL 开放，
  商用前请法务确认；
- **USDA CC0** 不要求署名，但官方"请求"标注来源；
- **Unlicense** 无义务；
- **指南类文本**不要整段复制进库，用"摘要 + 原文链接"；
- **CFCT** 是版权图书，不买授权不要入库。
