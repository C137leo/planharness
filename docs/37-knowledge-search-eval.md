# 43 条知识库的检索评测：为什么把加权关键词换成了 BM25

## 0. 结论先说

- 13 条 smoke test 证明不了检索质量，只证明"这 13 句没坏"；
- 补到 **84 条**（74 条可回答 + 10 条无答案）后，第一版手写加权分是
  **hit@1 82%、hit@3 96%**；
- 换成 **BM25 + 标题重复 + body_part 加分 + 阈值** 后是
  **hit@1 92%、hit@3 100%、MRR 0.971**；
- 所以**不是"为加权关键词辩护"，而是评测把它否了**，线上 `retriever.search()`
  已经改成 BM25；
- 但还有两个没解决：清单型问法 top1 90%、无答案问题误返回 7/10。
  这两件事不能靠调 BM25 参数解决。

复现：

```bash
cd backend
.venv/bin/python scripts/eval_knowledge.py
.venv/bin/python -m pytest tests/test_knowledge_eval.py -q
```

## 1. 为什么 13 条不够

原来的 13 条是围着知识库标题写的：

```
深蹲的时候膝盖疼怎么办
卧推肩膀疼可以换什么动作
手腕疼还能做俯卧撑吗
...
```

它们能证明"已知场景没坏"，但不能回答三个问题：

1. **换说法还能不能找到？** "训练前怎么热身"不是标题词，旧打分器 top1 是
   `protein-training`，因为"训练"在它标题里反复出现；
2. **同部位不同严重程度会不会串？** "膝盖肿了"应该先命中 `knee-redflag`，
   旧打分器 top1 是 `knee-pain-swap`；
3. **知识库没有答案时会不会硬返回？** 旧实现里"今天天气怎么样"能命中
   `protein-basics`——因为单字"天"在"每天"里。13 条里没有这种用例。

所以评测集必须覆盖：字面、改写、安全分级、营养结论、清单、无答案六类。

## 2. 评测集怎么设计

文件：`backend/data/knowledge/eval_queries.json`（84 条，人工标注）

| 类别 | 条数 | 测什么 | 例子 |
|---|---|---|---|
| literal | 18 | 术语/标题级问法 | "深蹲的动作要领" |
| paraphrase | 20 | 换说法、不照标题说 | "膝盖一蹲就疼，有什么动作能换" |
| safety | 12 | 同部位不同严重程度 | "膝盖肿了还能练吗" vs "膝盖打软腿" |
| nutrition | 14 | 结论 + 清单不串台 | "健身的人蛋白质吃多少" |
| list | 10 | 聚合清单条目 | "练胸有哪些动作" |
| out_of_scope | 10 | 没有答案时会不会硬答 | "肌酸怎么吃" |

每条三个字段：

```json
{
  "query": "膝盖一蹲就疼，有什么动作能换",
  "category": "paraphrase",
  "body_part": "knee",
  "expected_ids": ["knee-pain-swap"],
  "primary_ids": ["knee-pain-swap"],
  "note": "只考替代，不考红旗"
}
```

- `expected_ids`：**可接受答案**，top3 命中任一即算 hit@3；
- `primary_ids`：**理想答案**，top1 命中才算 hit@1；
- `out_of_scope`：`expected_ids` 为空，单独统计误返回率，不混进 hit。

几个刻意的标注原则：

- **宽泛问题允许多个答案**："蔬菜水果怎么选"接受蔬菜清单或水果清单；
- **不把"相关"当"正确"**："膝盖疼吃什么药"命中了膝痛条目也不算答对，
  因为它没有回答用药问题；
- **无答案问题不强行标一个 id**：否则会把"硬答"算成命中。

## 3. 指标定义

- **hit@1**：top1 是否命中 `primary_ids`；
- **hit@3**：top3 是否命中 `expected_ids`；
- **MRR**：首个可接受答案排名的倒数均值（没命中记 0）；
- **无答案误返回率**：`out_of_scope` 中 `search()` 仍返回结果的比例。

hit@1 衡量"第一眼对不对"，hit@3 衡量"给模型/答案三条候选够不够用"。
两个都看，避免用 hit@3 掩盖 top1 很差。

## 4. 评测结果

### 4.1 改前 vs 改后

| 方法 | hit@1 | hit@3 | MRR |
|---|---|---|---|
| 旧：手写加权（标题 3 / 标签 2 / 正文 1） | 82% | 96% | 0.903 |
| 新：BM25 + 标题重复 + body_part + 阈值 6 | **92%** | **100%** | **0.971** |
| BM25（无标题重复、无 body_part） | 88% | 100% | 0.957 |
| BM25 + body_part（无标题重复） | 88% | 100% | 0.957 |

结论：**旧打分器在每个类别上都不如 BM25**；"标题重复"和"body_part"各自都有贡献，
但最大的一步是换掉手写权重、用 IDF 和长度归一化。

### 4.2 分类别（新实现）

| 类别 | hit@1 | hit@3 | n |
|---|---|---|---|
| literal | 100% | 100% | 18 |
| paraphrase | 85% | 100% | 20 |
| safety | 92% | 100% | 12 |
| nutrition | 93% | 100% | 14 |
| list | 90% | 100% | 10 |

注意：**100% hit@3 不代表生产 100%**。只有 43 条语料、74 条人工问题，
top3 本来就容易覆盖；这个数字是"回归基线"，不是线上准确率。

## 5. 旧实现为什么输

| 查询 | 旧 top1 | 期望 | 原因 |
|---|---|---|---|
| 训练前怎么热身 | `protein-training` | `warmup` | 没有 IDF，"训练"在长条目里反复出现，分数越堆越高 |
| 晚上睡不够会影响训练吗 | `protein-training` | `sleep-recovery` | 同上，"训练"抢分 |
| 卧推肩膀疼可以换什么动作 | `bench-cue` | `shoulder-swap` | 标题"卧推"+3 压过 body_part 的 +2 |
| 膝盖肿了还能练吗 | `knee-pain-swap` | `knee-redflag` | 只按词面，不分"替代"和"就医信号" |
| 今天天气怎么样 | `protein-basics` | 无 | 单字"天"命中"每天"，阈值 2.0 太低 |

根因是四个：

1. **没有 IDF**：高频词和低频词一个价；
2. **没有长度归一化**：长条目重复词多，天然占便宜；
3. **权重是拍的**：标题 3、标签 2、正文 1 没有数据依据；
4. **单字噪声 + 阈值低**：一个"天"就能过阈值。

BM25 把前三个变成公式：tf 饱和、长度归一化、idf 加权；标题重复和 body_part
是还剩两个需要显式处理的信号。

## 6. 改后的实现

`app/knowledge/retriever.py`：

```python
BM25_K1 = 1.5
BM25_B = 0.75
BM25_MIN_SCORE = 6.0

# 文档文本 = 标题（重复一次）+ 正文 + tags
docs = [tokenize(" ".join([row.title, row.title, row.content,
                           " ".join(row.tags or [])])) for row in rows]
# 标准 BM25 + body_part 加分（同部位 +2，general +0.5）
```

为什么标题重复：43 条语料里标题就是最强意图信号，BM25 本身不区分字段；
实测纯 BM25 88%，标题重复后 92%。

为什么阈值 6.0：在 84 条上试了 0/4/6/8/10/12…，
6.0 不损失 hit@1/hit@3，同时挡掉"今天天气""帮我写 Python"这类完全无关问题；
再往上会误伤"腿怎么练"这种短查询。

## 7. 还没解决的

1. **清单型 top1 90%**："肩膀怎么练" top1 是 `shoulder-swap`，
   清单 `kb-ex-shoulder` 只排第二。可以加"怎么练/有哪些"的清单意图规则，
   但只在一条用例上验证过，暂时不加，避免过拟合。
2. **营养 top1 93%**："健身的人蛋白质吃多少" top1 是 `protein-basics`，
   不是 `protein-training`。需要"健身/增肌/训练"意图加权。
3. **安全 top1 92%**："膝盖肿了" top1 是替代条目而不是红旗条目，
   需要"肿/麻/响/晕"的红旗意图加权。
4. **无答案误返回 70%**：`search()` 是召回接口，不是问答接口；
   "膝盖疼吃什么药"返回膝痛条目是相关召回，不是答案。
   真正该管的是 `/knowledge/ask` 的拒绝逻辑——目前它只对
   胸痛/晕厥/用药/诊断等少数词做分流，覆盖不够。
5. **评测集是手写的**：84 条覆盖了六类，但没有真实用户日志；
   标注也可能有偏差。下一步应在线收集 query，再扩到 200+。

## 8. 为什么不直接上 embedding

- 43 条语料，BM25 已经 hit@3 100%、hit@1 92%，再换向量的增量空间很小；
- 真正的短板是"计划型问题"（"新手先练什么"）和"无答案拒绝"，
  这两个是**语料/流程问题**，不是检索算法问题；
- 换 embedding 要引入模型调用、pgvector、索引和延迟，先得用同一套 84 条
  证明它比 BM25 高，否则就是为技术而技术。

## 9. 面试怎么说

### 30 秒

> "最开始线上是手写加权关键词，13 条 smoke test 看着全过。后来我补到 84 条：
> 18 条字面、20 条改写、12 条安全分级、14 条营养、10 条清单、10 条无答案。
> 结果旧实现 hit@1 只有 82%，hit@3 96%；换成 BM25 + 标题重复 + 部位加分后
> 92% / 100%。所以我把旧打分器换掉了，没有为它辩护——评测就是用来否方案的。"

### 追问"为什么一开始不用 BM25"

> "第一版只有 13 条用例，都是围着标题写的，加权分看着够用；
> 补了改写和无答案用例后才暴露没有 IDF、长度归一化的问题。
> 这是我做评测的直接收获：**smoke test 只能防回归，不能选方案**。"

### 追问"100% 是不是过拟合"

> "是这套 84 条上的 100%，不是线上 100%。语料只有 43 条、top3 又宽，
> 100% 不稀奇；真正的缺口在清单 top1、营养 top1 和无答案拒绝。
> 所以我把它定位成回归门禁，不是效果宣传。"
