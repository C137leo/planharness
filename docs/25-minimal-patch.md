# 最小补丁（Minimal Patch）：改哪几处、凭什么说"最小"、面试怎么讲

## 1. 一句话定义

**最小补丁 = 在不可变的计划版本上，只替换"用户意图真正需要改的那些槽位"，其余内容从上一版
原样复制，最后以一个"新版本"提交（不是原地修改）。**

它要同时满足三件事，缺一不可：

1. **改动集合最小**：改动的槽位数 = 意图的"必要闭包"，不多改一个；
2. **其余不变**：没被点名的槽位走 **copy-forward**（复制上一版），而不是让模型重新生成；
3. **可回滚**：新版本有 `parent_version`，旧版本标记 `superseded` 但不删除。

## 2. 你的理解对不对

> "只修改某一个环节，其他内容不变" —— 方向对，但有两个细节要修正。

- **"最小"不等于"只改一处"**。比如"膝盖不舒服，别安排深蹲"可能是**换 1 个动作**；
  "今天想休息"要**把 3 个训练槽位都换成拉伸**；"不吃红薯"会**跨多餐换主食**。
  最小指的是"必要闭包最小"，不是"改动条数最少"。
- **"其他内容不变"是机制保证的，不是模型自觉**。做法是把上一版的动作快照 load 出来，
  只对 `operations` 里点名的 `slot_key` 做替换/删除，剩下的整份复制过去
  （`_new_version_from_actions(..., meals_from=base_version)` 连餐食也一起复制）。

所以准确说法是：**"以版本为单位的、受控的、可审计的最小变更"**。

## 3. 怎么做到的

```
用户一句话
  → 解析成结构化意图（intent）
  → 生成受控操作清单 operations（受控 DSL，不是自由文本）
        [{"op":"replace_action","slot_key":"5:strength:1",
          "before_action_ref":"leg-press",
          "after_action":{"action_ref":"stretch","duration_min":15},
          "reason":"今天以休息为主，训练换成拉伸"}]
  → 在动作快照上应用（_apply_operations），得到 proposed
  → 算 diff / churn（_diff）
  → 确定性安全门（膝痛禁忌、可用天数…），不过就 422 拒绝
  → 落 PlanPatch 草稿（pending_approval），不写版本
  → 人工审批 → 重跑安全门 → 生成新版本（copy-forward 其余槽位）
  → 写审批记录 + 审计链（approval_granted / patch_committed）
```

关键设计点：

| 设计 | 为什么 |
|---|---|
| 受控 DSL（`remove_action` / `replace_action`） | 模型不能写任意修改，只能"点名单个槽位" |
| `before_action_ref` 乐观并发校验 | 草稿期间计划被别的操作改过 → `stale patch`，拒绝覆盖 |
| 审批前不落版本 | 补丁是"提案"，用户确认才生效 |
| 审批时**重跑**安全门 | 防草稿期与审批期之间的状态漂移 |
| copy-forward + 新版本 | 其余内容不变是可验证的，而且历史不被改写 |
| 回滚 = 用旧内容再提交一个新版本 | 指针不回退，审计链保持纯追加 |

代码位置：`backend/app/domain/patches.py`（`_apply_operations` / `_diff` / `_safety_check` /
`approve_patch` / `_new_version_from_actions` / `rollback_plan`）、
`backend/app/domain/requests.py`（一句话 → intent → 草案）、
`backend/app/domain/draft_edits.py`（显式编辑解析，如"把深蹲换成臀桥"）。

## 4. "最小"的量化证据

`_diff` 输出四个指标：

| 指标 | 含义 |
|---|---|
| `total_slots` | 计划总槽位数（如 9） |
| `changed_slots` | 真正变了的槽位数（新增/删除，或 ref/sets/reps/duration 变了） |
| `churn` | `changed / total`，越低扰动越小 |
| `required_changes` | 意图的"必要改动数"（由调用方给出） |
| `unnecessary_churn` | `max(0, changed - required) / total`，**理想值为 0** |

真实一次（"今天想休息"，v21 → v22）的 Console 数据：

```
churn 33%   改动槽位 3/9   操作数 3   基于版本 v21
原计划 9 个槽位，改了 3 个，其余 6 个原样保留；必要改动 3 处，多余扰动 0%。

替换 腿举       → 全身拉伸   5:strength:1 · 今天以休息为主，训练换成拉伸
替换 罗马尼亚硬拉 → 全身拉伸   5:strength:2 · 今天以休息为主，训练换成拉伸
替换 俯卧撑      → 全身拉伸   5:strength:3 · 今天以休息为主，训练换成拉伸
```

`churn=33%` 说明"确实只动了三分之一"，`unnecessary_churn=0` 才是"没有多改"的证据。

## 5. 在 Console 里怎么看

打开 Console（`/pages/console/index`），选一条 `patch_approval` / `patch_rejection` 运行：

1. **TRACE**：`load_request → safety_check → commit v22`，补丁走了哪几步；
2. **DIFF · 最小补丁**：churn / 改动槽位 / 操作数 / 基于版本 + 上面那段中文改动清单；
3. **CONTEXT**：上下文预算（补丁场景会记录快照；快捷动作这种确定性路径没有，会显示"没有上下文快照"）；
4. **COST**：tokens / 成本（确定性路径是 0，说明没花模型钱）；
5. **VERIFICATION**：独立验证的检查项；失败会触发自动回滚（老补丁链路才有，新链路这块还没接）；
6. **AUDIT CHAIN**：`approval_granted` / `patch_committed` 等事件 + 哈希链校验按钮，
   能证明"谁在什么时候放行的哪一版"。

> 之前 Console 的 DIFF 卡只显示数字（操作数 3），看不到"到底改了哪几处"；
> 现在补上了改动清单，并把 `patch_id` 记到了审批 run 的 output 里，新链路也能对上。

## 6. 面试怎么讲（30 秒版）

> 这个项目里"改计划"不是让模型重写整份计划，而是生成一条**最小补丁**：
> 模型只输出受控操作（替换/删除某个槽位），代码把它应用到当前版本的快照上，
> 其余槽位原样复制，产出新版本。
> 这样有三个好处：**改动可读**（一个 diff 就能评审）、**扰动可量化**
> （churn 33%、多余扰动 0%）、**可回滚可审计**（新版本有父版本，审计链纯追加）。
> 安全上是双门：生成时一次确定性安全门，人工审批时再重跑一次，模型没有放行权。

## 7. 常见追问与答法

**Q：为什么不直接让模型重新生成一份计划？**
A：三个问题。①不可评审——整份计划变了，用户/审核者看不出"到底改了什么"；
②不稳定——同一句话两次生成结果不同，历史版本之间失去可比性；
③贵且慢——重生成要重新跑营养/动作编排。补丁把"变更"变成一阶公民。

**Q：模型改错了怎么办？**
A：改错有三道拦：受控 DSL 让模型只能点名槽位（写不出非法结构）；
确定性安全门独立判断（膝痛禁忌、天数、热量目标一致性），不看模型的话；
人工审批必须点确认，审批时安全门再跑一次。

**Q："必要改动数"谁定？**
A：由意图/场景给出（"今天想休息"= 当天所有训练槽位；"换一个部位"= 涉及的动作数），
不交给模型自评，否则模型会把自己的过度改动解释成"必要"。

**Q：怎么验证"最小"不是嘴上说说？**
A：`unnecessary_churn` 是指标：`(实际改动 - 必要改动) / 总槽位`，评测里要求均值 ≤ 0.30，
单场景断言 `unnecessary_churn == 0`；另外有 mutation/回归测试保证安全门不被改松。

**Q：copy-forward 会不会把过期内容带进来？**
A：会，所以有 `base_version` 比对 + `before_action_ref` 乐观校验：草稿基于 v21，
审批时计划已是 v22 → 直接 `stale patch` 拒绝，而不是默默覆盖。

## 8. 已知边界（面试时主动说，比被问出来好）

- 新链路（`patch_requests`）目前**没有接独立验证器**，Console 的 VERIFICATION 只对老链路有；
- `required_changes` 依赖场景/意图人工给定，意图解析错了这个指标就没意义；
- 补丁只支持动作层的 `remove/replace`，`add` 与餐食层的补丁还没做（餐食走另一条
  "选餐食"链路，也是新版本 + 可回滚）。
