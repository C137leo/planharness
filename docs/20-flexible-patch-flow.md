# 20 一句话改计划：从「固定补丁」到「可协商草案」

> 这篇回答一个问题：为什么原来那套「一个膝痛场景 + 一个固定补丁」不够用，改成什么样了。

## 1. 原来的问题

旧流程是：用户点「生成膝痛补丁」→ 后端写死一个 `knee_patch` 场景 → 前端只能通过/拒绝。

三个硬伤：

1. **人口太窄**：只有「膝痛 + 只能练 2 天」这一个入口，用户想休息、想换动作、想加量都没有路径。
2. **改不了**：草案不满意只能拒绝重来，没有一个「再改改」的往返。
3. **写在代码里**：补丁内容是常量，等于把业务判断写死在演示脚本里，看不出 Agent 在哪。

## 2. 现在的流程

```
一句话 / 快捷入口
      │
      ├─ parse_intent（规则表，可换成 LLM，接口不变）
      │
      ├─ 需要澄清？ → 追问一句（不产草案）
      │
      ├─ plan_operations → 最小操作集（replace / remove）
      │
      ├─ 安全门：受伤部位、可用天数、过敏原  → 不通过就明说原因
      │
      └─ 草案（pending_approval，计划不动）
              │
              ├─ 再改改（≤3 轮，每轮基于同一 base_version 重新规划，旧草案 superseded）
              ├─ 确认应用 → 新版本 + 审批留痕 + 审计链
              └─ 取消 / 拒绝 → 计划不受影响

撤销：/plans/{id}/undo → 内容回到父版本，但**再生成一个新版本**（append-only）
```

三条不变量（改设计时先看这个）：

| 不变量 | 含义 |
| --- | --- |
| 草案不写版本 | 只有 `approve` 才会产生 `plan_versions` 新行 |
| 安全门是确定性的 | 模型只提议；受伤部位/天数/过敏原由代码判定 |
| 历史只增不改 | 撤销也是新版本，`superseded` 只改状态不删行 |

## 3. 新增的表

| 表 | 作用 |
| --- | --- |
| `patch_requests` | 一次「一句话改计划」的请求：原文、意图、轮次、状态、指向的草案补丁 |
| `patch_feedback` | 每一轮「再改改」的原话，用来复盘为什么改了 3 轮 |
| `workout_logs` | 真的练了什么（动作、时长、类型），热量只从这里算 |

`patch_requests.status`：`clarifying`（待补充）→ `ready`（草案可审批）→ `applied` / `rejected`；
被新一轮取代的草案补丁状态变 `superseded`，不会留在「待确认」列表里。

## 4. 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/plans/{plan_id}/patch-requests` | 一句话 → 草案 / 追问 / 被拦；`base_version` 可做乐观锁 |
| GET | `/patch-requests/{id}` | 取草案（前端刷新/恢复用） |
| POST | `/patch-requests/{id}/feedback` | 再改改，≤3 轮，超过 422 |
| POST | `/patch-requests/{id}/approve` | 确认应用 → 新版本 |
| POST | `/patch-requests/{id}/reject` | 拒绝草案，计划不动 |
| POST | `/plans/{plan_id}/undo` | 撤销上一次提交（生成新版本） |
| POST | `/workout-logs` | 记一条训练 |
| GET | `/workout-logs?days=14` | 最近的训练记录 |
| DELETE | `/workout-logs/{id}` | 记错了能删 |
| GET | `/stats/calories?days=7` | 热量统计（只算消耗） |

旧的 `/plans/{id}/patches`、`/patches/{id}/approve` 等接口保留：它们是底层原语，
`patch-requests` 只是多加了一层「可协商」的入口，两者共用同一套审批、验证、审计。

## 5. 热量口径

```
kcal = MET × 3.5 × 体重(kg) / 200 × 时长(min)
```

- **只算消耗**，不含基础代谢、不含饮食摄入；接口返回 `scope: "burn_only"` 把这件事说清楚。
- MET 是常量表（`app/domain/calories.py`），没收录的动作走兜底值 4.0 并标 `met_fallback: true`。
- 体重口径优先级：最近一次打卡 > 画像 > 默认 70kg，返回里带 `weight_source`。
- 热量**不落库**：读取时用当时的体重算，避免体重变了旧记录口径对不上。

## 6. 三个设计问题的默认答案

| 问题 | 默认 | 理由 |
| --- | --- | --- |
| 热量只算消耗还是也算摄入 | 只算消耗 | 摄入误差比消耗还大；先给一个可信的数，加摄入是加字段不是改口径 |
| 「当前目标」是否唯一 | 是，只有 1 个 active goal | 多目标会让「补丁改的是哪个目标」变得不可判定 |
| 是否接受 uni-app | 是 | 同一套代码出 H5 + 小程序；换成 React 只得到 H5，还得重写一遍 |

## 7. 前端对应的改法

TabBar 从「今天/打卡/审批」改成 **今天 / 计划 / 进展 / 我的**：

- **审批不再是独立 tab**：它是「改计划」这个动作的最后一步，做成底部抽屉（`PatchComposer.vue`）。
  抽屉里依次是：输入 → 草案（改动清单 + 风险 + 解释）→ 再改改 / 确认应用。
- **今天**：只显示今天的动作 + 今日已记录消耗，快捷按钮带预设说法打开抽屉。
- **计划**：整周明细、待确认改动、撤销上一次改动。
- **进展**：近 7 天消耗柱状图、体重、最近训练记录，并显示热量公式与口径。
- **我的**：画像、器械、过敏原，以及「这个 demo 的真实边界」。

交互上有一条踩过坑的规则：**审批动作绝不自动跳转**。之前「生成补丁」后自动切 tab，
审批按钮正好落在刚点过的位置，连点两下就会直接提交。现在草案必须由用户亲手点「确认应用」。
