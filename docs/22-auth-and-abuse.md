# 22 注册 / 登录：防刷不是加个验证码

> 目标很具体：**别让脚本把数据库打爆**。下面每一层都对应一种真实攻击方式。

## 1. 威胁模型（先写清楚防谁）

| 攻击 | 表现 | 这一层的应对 |
| --- | --- | --- |
| 脚本批量注册 | 一个脚本循环 POST，几秒钟上千个账号 | 单 IP 每小时/每天配额、全站熔断、账号总数硬上限 |
| 撞库 | 拿手机号 + 密码字典反复登录 | 登录失败计数 + 锁定，成功即清零 |
| 重放 / 复用表单 | 同一个请求体反复发 | 一次性票据，用后即废 |
| 无脑填表机器人 | 几十毫秒就"填完"注册表单 | 服务端签发的票据带时间戳，检查最短填表耗时 |
| 占号 / 重复提交 | 同号反复提交注册 | 同手机号每天 3 次配额 |
| 请求体撑爆 | 超大 JSON | 只收必要字段（Pydantic 限长），失败请求也计数 |

**挡不住的（诚实说明）**：分布式 IP 池、真人打码平台、短信轰炸。
那需要短信验证码、WAF / 风控服务，不是应用层能独立解决的。本 demo 没有短信通道，
所以注册不校验验证码——这一点在登录页上也明写着。

## 2. 四道闸口

```
请求
 ├─ 1. 账号总量上限（MAX_USERS）          → 503，一个字节都不写库
 ├─ 2. 全站熔断（每小时注册数）            → 429 + Retry-After
 ├─ 3. 分层限流（IP 时/日、手机号 日、登录失败）→ 429 + Retry-After
 ├─ 4. 一次性票据（签名 + 有效期 + 最短耗时）  → 400
 └─ 5. 密码策略 + 唯一性                   → 422 / 409
```

两个刻意的顺序：

- **先花调限额，再验票据，最后才查库**。无论攻击者怎么失败，成本都记在限流器上，
  数据库只承担通过限流的那部分请求。
- **失败请求也计数**。限流器用独立 Session 提交，不跟业务事务一起回滚；
  否则"故意用弱密码让请求失败"就能绕过限流。

## 2.1 默认限额（页面上不写这些，避免打扰用户）

| 项 | 默认值 | 说明 |
| --- | --- | --- |
| 单 IP 成功注册 | 5 / 小时、15 / 天 | **只统计写库成功的注册** |
| 同一手机号成功注册 | 3 / 天 | 防占号 |
| 全站成功注册 | 200 / 小时 | 熔断，保护数据库 |
| 单 IP 尝试次数 | 20 / 小时、60 / 天 | 含失败请求，只防刷接口 |
| 登录失败 | 8 次 / 15 分钟 | 超限锁 15 分钟 |
| 账号总数 | 5000 | 到顶 503 |
| 票据获取 | 30 / 分钟 | 票据接口本身也会被刷 |

> **为什么"失败不扣成功配额"**：第一版把两者混在一起，结果用户连着几次
> 「提交太快」就把整小时的注册额度用完了，自己把自己锁死；反过来攻击者也能
> 用失败请求把别人的配额耗尽。现在成功配额只在写库成功后计数，失败请求另走
> 「尝试次数」这条更宽松的线。

演示时如果被自己的试错锁住，用这个恢复（仅 `ENV=dev/test` 可执行）：

```bash
cd backend
.venv/bin/python scripts/reset_rate_limits.py --yes
```

> 改完配额逻辑后**必须重启后端**才生效（uvicorn 不加 `--reload` 不会自动重载）。
> 判断是否已生效：一次失败注册只应新增 `register:try:ip:*`，
> 不应再出现 `register:ip:*` / `register:phone:*`。

## 3. 实现要点

### 一次性票据（`app/abuse.py`）

```
GET  /api/v1/auth/challenge?purpose=register|login
 → {challenge_id, token, expires_in, min_fill_ms}
```

`token = HMAC-SHA256(SECRET_KEY, "challenge_id|purpose|issued_at_ms")[:40]`。
服务端校验五件事：存在、用途匹配、未使用、未过期、签名正确；
再看「从签发到提交」的耗时是否小于 `AUTH_MIN_FILL_MS`（默认 1200ms）。
真人不至于 1 秒内填完手机号 + 密码，机器通常只要几十毫秒。

挑战签发本身也限流（同 IP 每分钟 30 次），否则它就成了新的放大器。

### 分层限流（`RateLimiter`）

固定窗口计数器，主键是 `scope:identifier@window_start`：

| 键 | 默认上限 | 窗口 |
| --- | --- | --- |
| `register:ip:{ip}` | 5 | 1 小时 |
| `register:ipday:{ip}` | 15 | 1 天 |
| `register:phone:{phone}` | 3 | 1 天 |
| `register:global` | 200 | 1 小时 |
| `login:fail:{ip}:{phone}` | 8 | 15 分钟（超限锁 15 分钟） |
| `challenge:ip:{ip}` | 30 | 1 分钟 |
| `demo:ip:{ip}` | 10 | 5 分钟 |

窗口过期行由限流器每 5 分钟顺手清理，表大小只和"活跃键"有关，不随攻击量增长。

### 账号上限

`MAX_USERS`（默认 5000）到顶直接 503。这是最后一道保险：
即使限流被绕过，磁盘也不会被写满。

### 密码策略

8–72 位、必须含字母和数字、不在常见弱口令表里、不包含手机号、重复字符不超过 3 种。
刻意不要求"大小写 + 符号"——那类规则带来的收益通常小于用户把密码写在便利贴上的损失。

## 4. 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/auth/challenge` | 申请一次性票据（含最短填表时间） |
| POST | `/api/v1/auth/register` | 注册：票据 + 手机号 + 密码 + 蜜罐字段 |
| POST | `/api/v1/auth/login` | 登录：失败计数与锁定 |
| GET | `/api/v1/auth/me` | 当前账号（手机号 / 昵称 / 是否有画像） |
| POST | `/api/v1/auth/demo` | 演示账号（同样按 IP 限流） |

429 响应统一带 `Retry-After`，前端据此倒计时，而不是盲目重试。

## 5. 为什么这么设计（从页面挪到这里）

登录页上原先有一段"防滥用限制"说明和一张"为什么这么设计"的卡片，太占地方，
也不该让用户在注册时读架构说明。挪到文档里：

- **一次性票据**：提交前申请、服务端签名、只能用一次，脚本没法伪造"填表耗时"；
- **分层限流**：IP / 手机号 / 全站三层固定窗口，超限返回 429 + Retry-After；
- **失败的请求也计数**：计数器独立提交，不会跟着业务事务回滚，没法靠"故意失败"刷；
- **账号总量上限**：到顶直接 503，数据库不会无限增长。

## 6. 前端

`pages/login/index.vue`：

- 登录 / 注册切换，注册时显示密码强度条与人话提示；
- **页面打开时就申请票据**，提交时复用——用户输手机号 + 密码的时间就是填表耗时；
  如果点得太快（浏览器自动填充后立刻点），会自动等 1.4 秒用同一张票据重试一次；
- 蜜罐字段放在屏幕外，正常用户看不到，脚本会把所有 input 填满；
- 429 时按 `Retry-After` 倒计时并禁用提交；
- 「先用演示账号看看」走 `/auth/demo`，同样受限流约束；
- 登录成功后存 token 并回到「今天」；没登录直接访问任意页会被送回登录页。

## 7. 验证

```
tests/test_auth_abuse.py   20 条
  ├─ 无票据 / 票据复用 / 提交过快 / 过快被拒后同一票据可重试成功
  ├─ 密码策略 5 组参数化（长度、字母数字、常见、含手机号、重复字符）
  ├─ 手机号格式、蜜罐、重复手机号
  ├─ IP 小时配额 429 + Retry-After
  ├─ 手机号日配额、全站熔断、MAX_USERS 上限
  ├─ 登录锁定、成功清零、不泄露手机号是否存在
  └─ 挑战接口自身限流
```

真实服务上手工验证（uvicorn，默认配置）：

| 场景 | 结果 |
| --- | --- |
| 申请票据后立刻注册 | 400「提交太快了」 |
| 申请票据 → 等 2 秒 → 注册 | 200，直接可用该 token 调 `/auth/me` |
| 同 IP 第 6 次注册 | 429「注册太频繁」，带 `Retry-After` |

全量回归：`pytest` **135 passed / 1 skipped**。

## 8. 没做 / 下一步

- **短信验证码**：需要短信服务商；现在注册没有验证码，只有上面的限流与票据。
- **密码找回**：demo 阶段没有自助找回（登录页已明示）。
- **分布式限流**：计数器在数据库里，多实例部署天然共享；但高 QPS 下应换成 Redis。
- **风控评分**：设备指纹、行为序列、IP 信誉——超出这个 demo 的范围。
